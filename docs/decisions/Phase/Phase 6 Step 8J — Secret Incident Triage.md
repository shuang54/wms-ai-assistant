# Phase 6 Step 8J — Secret Incident Triage

## 目标

调查 GitGuardian Security Checks 报告的 7 个疑似秘密信息，判断其类型、来源、有效性及影响范围。

## 严格限制

- 不修改文件。
- 不创建提交。
- 不推送。
- 不重写 Git 历史。
- 不绕过 GitGuardian。
- 不合并 PR。
- 不输出秘密值、API Key、密码、Token 或连接字符串。
- 不把生产凭据复制到报告。

## Step 1：核对 GitHub 检查

在对应的 GitHub 页面打开失败的 `GitGuardian Security Checks`，记录每条告警的：

- 告警编号或安全事件 ID
- 秘密类型
- 涉及的文件路径
- 涉及的 commit SHA
- 首次出现的提交
- 当前是否仍存在于分支
- GitGuardian 标记的有效性状态（如果提供）

报告中只记录元数据，不记录秘密值。

## Step 2：检查 Git 历史

在本地仓库只读检查相关提交和文件路径。

重点确认：

- 告警是否来自测试 fixture、示例配置、文档或真实运行配置
- 是否存在硬编码 API Key、数据库凭据、Token 或其他敏感信息
- 告警涉及的提交是否属于本次 Phase 6 提交链
- 同一秘密是否在后续提交中被删除，但仍保留于 Git 历史

不要将完整文件内容或疑似秘密打印到终端报告。

## Step 3：判断处置级别

对每条告警分类：

- `CONFIRMED_SECRET`
- `LIKELY_FALSE_POSITIVE`
- `NEEDS_OWNER_VERIFICATION`

如果属于真实凭据，立即通知凭据所有者并通过对应服务的安全渠道撤销或轮换。不要等待代码清理完成后才处理有效凭据。

如果无法判断，不得自行标记为误报。

## Step 4：核对 PR 状态

只读确认：

- 当前是否存在对应 PR
- PR 的源分支与目标分支
- GitGuardian 检查的最终状态
- 是否存在其他失败的必需检查
- 当前是否已经合并

不要创建、关闭或合并 PR。

## Step 5：最终报告

逐项报告：

1. 7 条告警的分类与元数据
2. 涉及的提交和文件路径
3. 是否确认存在真实凭据
4. 真实凭据是否已撤销或轮换（仅报告确认结果）
5. 是否存在历史提交残留
6. PR 当前状态
7. 哪些事项仍需凭据所有者或仓库管理员处理
8. 建议的最小修复方案

调查完成后立即停止。不得修改 Git 历史、提交修复或推送新内容，等待新的明确授权。
